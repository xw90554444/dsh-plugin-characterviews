# 角色多视图 Character Multi-View

上传一张人物照片，在本机 ComfyUI 上把同一个人物从不同角度画出来。

- **单视图** —— 一个角度，正面 / 侧面 / 背面，或用滑杆指定任意角度
- **三视图** —— 正面 + 侧面 + 背面
- **多视图** —— 正面 + 侧面 + 背面 + 仰视 45° + 俯视 45°
- **任意角度** —— 自己组合最多 8 个角度

三视图与多视图有两种出图方式：**一张设定图**（所有角度画在同一张图里，比例、光照、
服装最统一，默认）或**每角度一张**（分辨率更高，某一张不满意可以单独重抽）。

出图、预览、保存、打开文件所在位置，全部在本地完成，不联网、不上传任何东西。

## 它需要什么

| 需要 | 说明 |
|---|---|
| DSH | 已在运行（本说明以 `desktop` profile 为例） |
| Node | **>= 22**（`package.json` 的 `engines` 要求） |
| ComfyUI | 本机运行，默认 `http://127.0.0.1:8188`，可在设置里改 |
| 图像模型 | Qwen-Image 2.1 系列（扩散模型 + `qwen3vl` 文本编码器 + `qwen_image` VAE） |
| 关键节点 | `TextEncodeQwenImage21`（ComfyUI 自带） |
| 显存 | 建议 12 GB 以上空闲；不足也能出，只是慢——模型会分块搬到内存 |
| 放大模型（可选） | ESRGAN 系任一款放 `models/upscale_models/`，用于「高清放大」 |

第一次打开面板时它会自己检查这些，缺什么会直接写在面板顶上。

## 安装

### 装进 profile

DSH 的插件按 profile 安装，一个 profile 一个 `package.json`（`~/.dsh/profiles/<profile>/`）。
在 `dependencies` 与 `dsh.profile.bundles` **两处**都加上：

```jsonc
{
  "dependencies": {
    "dsh-plugin-characterviews": "link:D:/plugins/dsh-plugin-characterviews"
  },
  "dsh": { "profile": { "bundles": [ "...", "dsh-plugin-characterviews" ] } }
}
```

想跟着上游更新，用 `"github:xw90554444/dsh-plugin-characterviews"` 代替 `link:`。

装依赖（用 DSH 自带的 pnpm，避免版本不一致）：

```powershell
node "$env:DSH_HOME\dsh-runtimes\dsh-primary-runtime\dependencies\pnpm\bin\pnpm.mjs" install --dir "$env:DSH_HOME\profiles\desktop"
```

> **不需要改 profile 的 `cordis.patch.yml`。** 插件自带的 `cordis.patch.yml` 已声明
> 自己的条目（`- insert: id: characterviews`）并在 `package.json` 的
> `dsh.bundle.patch` 里注册，DSH 会自动应用。只有要**禁用**时才走 profile patch 层，
> 且按**包名**写：`- id: dsh-plugin-characterviews` / `disabled: true`。

### 重启

**宿主半边必须重启 DSH 进程**，刷新页面不够——它是 Node ESM 模块，模块缓存会留住旧代码。
客户端半边（界面）每次刷新页面重新加载，改界面只需 `Ctrl+R`。

它们不需要 ComfyUI 在跑，也不需要联网。测试数据是写死的夹具，不读你的真实角色。

## 为什么用 Qwen-Image 2.1

`TextEncodeQwenImage21` 的 `images` 是一个可挂 **16 张参考图**的输入组。也就是说：
同一个编码器既做文生图，也做参考图编辑。上传的照片作为参考图喂进去，模型在文本
编码阶段就"看到"这个人，同时照片还被拼进潜空间——人物一致性就是从这里来的，
不需要第二个模型、也不需要装任何自定义节点。

## 用法

1. 侧边栏点「角色多视图」。
2. 左侧「角色」里新建一个角色（名字会成为文件夹名）。
3. 把照片拖进虚线框，或点击选择。正面、清晰、全身的照片效果最好；一张就够。
4. 选视图模式：
   - **单视图**：点角度快捷键，或拖滑杆（水平角 0 正面 / 90 右侧 / 180 背面 / 270 左侧；俯仰角正数俯视、负数仰视）。
   - **三视图 / 多视图**：选「一张设定图」还是「每角度一张」。
   - **任意角度**：点选最多 8 个角度，按点选顺序排列。
5. 需要的话填「补充要求」，例如"保持这件深灰色圆领 T 恤""背景换成纯白"。
6. 点「开始出图」。任务面板会显示排队 / 采样 / 已完成，随时可以取消（取消会同时把它
   从 ComfyUI 队列里撤掉，不会留下一个没人等的 GPU 任务）。
7. 出图完成后，右边图库里点一张看图，可以**放大**、**打开文件所在位置**、**保存…**、**删除**。

## 图存在哪里

```
%USERPROFILE%\.dsh\characterviews\
├─ library.json              索引：角色、照片、每张出图、每一批用的角度与种子
├─ runs.json                 任务记录（重启后仍能看到"上次被中断"）
└─ characters\<角色名>\
   ├─ photos\<id>.<ext>      你上传的照片，原样保存不做二次压缩
   └─ views\<id>.<ext>       生成的图
```

ComfyUI 那边也始终留一份（它的 `SaveImage` 写在自己的 output 目录），设置页里能看到
那个路径。两处都在本机。

「保存…」的行为：图片本来就已经在磁盘上了，所以在没有指定目录时它会打开文件管理器并
选中这个文件；在设置里填了「图片另存目录」后，它会真的复制一份过去。

## 分辨率

「③ 出图」卡片顶部就是分辨率：**7 种比例 × 9 档长边像素**（512 – 2048）。旁边实时显示
实际输出尺寸，`长边像素` 指的是**单个视图**的长边。

| 比例 | @1024 | @1280 | @2048 |
|---|---|---|---|
| 1:1 正方形 | 1024×1024 | 1280×1280 | 2048×2048 |
| 3:4 竖版 | 768×1024 | 960×1280 | 1536×2048 |
| 4:5 人像 | 819×1024 | 1024×1280 | 1638×2048 |
| 2:3 长竖版 | 683×1024 | 853×1280 | 1365×2048 |
| 4:3 横版 | 1024×768 | 1280×960 | 2048×1536 |
| 3:2 宽横版 | 1024×683 | 1280×853 | 2048×1365 |
| 16:9 宽屏 | 1024×576 | 1280×720 | 2048×1152 |

几条规则：

- **只对齐长边**到 32 的倍数，短边按比例算。两条边都强行对齐的话 16:9 @1280 会变成
  1280×736 而不是 1280×720——差 16px 听起来无所谓，但它已经不是 16:9 了。
- **多视图时，分辨率描述的是每个视图**。三个视图 3:4 @768 会出一张 1728×768 的画布
  （3 格并排），每格都是 768 长边。界面上会写清楚"整张画布 ××××"。
- 最多 3 个视图一行，超过就折行（5 个视图 → 3×2）。单格宽了，人才看得清。
- 有**硬上限**：单边 2048px、总量 4MP（Qwen-Image 2.1 的原生上限）。放不下的档位**不会
  出现在下拉框里**——与其让你选一个 1536 然后悄悄给你 1408，不如根本不提供这个选项。
- 设置页里那份是**默认值**，出图卡片里改的只影响这一次，不会写回配置。

## 面板高度

**任务列表**和**图库**都是固定高度、可以拖动调整的。

- 抓住列表**上方那条短横条**上下拖：往上拖变高，往下拖变矮。
- 任务列表双击横条、或点「默认高度」回到 220px。
- 键盘也行：聚焦横条后 ↑/↓ 每次 16px，按住 Shift 是 64px。
- 范围 120 – 720px，配置里手改超范围也会被钳回。

图库默认是**「一行高」模式**：高度跟着缩略图那一行走，刚好显示一张图。

这一条不能用写死的像素值做。图库是 `minmax(140px, 1fr)` 的自适应网格，**格子宽度取决于面
板当前多宽**，而格子高度是宽度的 4/3。实测同一份代码：

| 面板宽 | 列数 | 单格 | 一行高 |
|---|---|---|---|
| 300px | 2 | 144×192 | 227px |
| 480px | 3 | 153×204 | 239px |
| 820px | 5 | 157×209 | 244px |
| 1024px | 6 | 163×218 | 253px |

所以写死 260 只是碰巧接近。插件改为**量出**一行的真实高度（量单个格子而不是整个网格——
网格有三行的话量的就是三行），并在窗口尺寸变化时重新量。

关键在于「一行高」被存成**模式**而不是数字：手动拖动横条会切到固定高度（这是明确的意图），
点「一行高」按钮切回自适应。否则一次测量结果被持久化之后，窗口一改宽度它就不对了。

图库固定高度不只是美观问题：它就排在预览下面，不限制的话每出一张图都会把预览往上顶，
最后你正在看的那张被挤出面板。任务列表同理，队列长了会把设置挤没。

## 看大图

图库里**单击**看图（进右上的预览），**双击**或点「放大」开全屏。

全屏遮罩是 **portal 到 `document.body`** 的，不是渲染在面板里——这一条是关键：面板里
`position:fixed` 只相对于最近的"包含块"生效，而壳的滚动容器带 `transform` 和 `overflow`，
恰好会建立包含块。原来的写法就是这样：遮罩被**裁在面板范围内**，尺寸却按整个浏览器窗口的
`94vw` 算，于是宽图被切掉、竖图缩在一个比看起来小得多的框里。

图片尺寸用 `max-width/height: 100%` 交给浏览器按真实视口解析，窗口或面板一改大小就自动跟着
变——比自己去量任何东西都可靠。

操作：滚轮缩放（1×–8×）、放大后拖动平移、双击在 1×/2× 间切换、`0` 或「适应」复位、`Esc` 关闭。

## 高清放大

选中的图（预览区那排按钮下面）有 **1.5× / 2× / 2.5× / 3× / 3.5× / 4×** 六档放大。

### 两步操作，防误碰

**点倍数只做选中，再点「开始放大」才真的跑。**

一次放大是几十秒的 GPU 任务，误触的代价不是一次点击，而是一段真实的等待（或一次取消、一个
被占用的队列位）。所以第一步免费，第二步才花钱：

```
高清放大  [1.5×] [2× ✓] [2.5×] [3×] [3.5×] [4×]     ← 点这里只是选中
          ┌──────────────────────────────────────┐
          │ 992×1312 → 1984×2624（5.2MP）         │     ← 要产出的尺寸就在提交按钮旁边
          │ [开始放大 2×]  [取消]                  │
          └──────────────────────────────────────┘
```

要点：

- **没选中倍数时不存在提交按钮**，所以无从误触。
- **要产出的尺寸就写在提交按钮旁边**。原来这些数字离按钮有一段距离，那正是容易点错的成因之一。
- 被上限钳制时，倍数按钮标真实倍数（`4× →2.63×`），提交按钮也写「开始放大 2.63×」。
- 「取消」只是取消这次选择，不发起任何请求。

### 为什么是 ESRGAN，而不是"高清修复"

因为你的要求是**主体不能有任何变动**，这一条直接决定了技术路线：

| 路线 | 原理 | 主体会不会变 |
|---|---|---|
| **ESRGAN 上采样**（本插件） | 纯卷积，在源像素定义的范围内合成细节，**没有采样/生成步骤** | 不会 |
| 扩散式"高清修复" / 超分 | 重新扩散采样，等于**重画一遍** | 会，脸会漂 |

所以没有做扩散那条路——它正是会改人的那种。

### 这不是口头保证，是可验证的

`wf_tools/measure_identity.py` 做**可逆性检验**：把放大图缩回原尺寸（4× 是精确的网格逆运算），
再逐像素比对。主体若被改动，这个平均值回不到原处。

实测（992×1312 → 3472×4592）：

```
主体是否改变
  平均差      1.091 / 255   = 0.43%
  99 分位差   10.0 / 255
  ✓ 主体未改变

是否真的更清晰（Laplacian 方差，只在同尺寸间比较才有意义）
  双三次放大（对照组）  4.05   ← "只是变大"长这样
  ESRGAN 放大          41.29  ← 高 10.2×，是真的加了结构
```

对照组很关键：**可逆性本身无法区分"加了细节"和"平滑放大"**——双三次放大也能通过可逆性
（平均差 0.281，比 ESRGAN 还小）。真正说明问题的是同尺寸下的清晰度差 10.2×。

### 原理和取舍

装的是 ESRGAN 系网络，**它们只会 4×**。所以流程是"先放大到 4×（细节在这一步加出来），
再用 lanczos 缩回你要的倍数"。1.5× 这种非整数倍就是这么来的——直接让缩放节点插值，只会把
图变大、不会更清晰。

结果**存成新图**，不覆盖原图：原图是"模型实际产出了什么"的记录，覆盖它会让种子和提示词
的历史变成假话。新图标签带倍数（`正面 · 4×`），条目上标"已放大 4×"，并且**不允许对放大图
再放大**——细节第一遍已经加过，再走一遍只是把文件变大。

照片不能放大——照片本身就是原图。

### 上限随显存自适应

**这一条是实测推翻了我原来的设定。** 我原本写死 16MP 上限，理由是"怕显存不够"。实测
（4070 Ti SUPER，7.3GB 可用，`4xNomos8k_atd_jpg`）：

```
768×1024  -> 3072×4096  (12.6MP)   21.2s   16.8MB
1536×1024 -> 6144×4096  (25.2MP)   36.3s   33.7MB
1536×2048 -> 6144×8192  (50.3MP)   72.5s   68.8MB
```

**50MP 只要 72 秒**，我那个上限把它砍掉了三分之二，而且砍的理由不成立。现在上限按**当时
可用的显存**算，并且**把上限显示在界面上**：

| 可用显存 | 上限 |
|---|---|
| 2 GB | 8MP / 单边 4096px |
| 4 GB | 12MP / 单边 8192px |
| 7.3 GB | 22MP / 单边 14950px |
| 14.6 GB | 44MP / 单边 16384px |
| 24 GB | 72MP / 单边 16384px |

系数取 **3 MP/GB，是刻意保守的**。实测那个点（7.3GB 空闲下 50MP 成功）看着像 7MP/GB，但那
是**空闲**显存而不是**用量**，而且显存不够时 ComfyUI 会往内存卸载——所以那次可能根本没用到
7.3GB。**一个观测点推不出比例关系**，与其外推，不如取比证据更小的一档：取 3MP/GB 时，实测
机器上允许的仍是最大实测请求的 4.4 倍，覆盖这里所有真实尺寸。判断错了只多一次重试（按钮上
写着每个倍数实际会产出多少），判断反了则是一次白等的失败。

超限时按钮上会写明**实际会得到的倍数**（例如点 4× 但标注 `→2.63×`），文件名也记真实的
2.63×——一个写着"4×"却悄悄给你 2.63× 的按钮，比一个直接说做不到的按钮更糟。

需要 `models/upscale_models/` 里有任一款 ESRGAN 系模型。没有的话按钮会禁用并说明原因。

## 删除是怎么回事（重要）

插件里有两种文件，它们的删除方式**故意不一样**：

| | 生成图（可重出） | 照片（不可再生） |
|---|---|---|
| 删除时 | 直接删归档副本 | **移到 `trash\`，不销毁** |
| 理由 | 批次里记着种子、提示词、角度、步数，能再出一张；ComfyUI 的 output 里另有一份 | 你提供的原图，没有任何东西能重新造出来 |
| 怎么彻底删 | 直接删就是彻底 | 在「设置 → 回收站」里再删一次，或清空回收站 |

删掉整个角色也一样：生成的图跟着删，照片进回收站。

**恢复是把两半一起还原的**：字节回到 `characters\<角色名>\photos\`，同时索引记录也重建
——只还原文件的话面板看不见它，等于没恢复。

如果回收站因为权限之类的原因没能接收文件，插件**不会**退化成直接删除，而是把文件留在
原地并明确告诉你它在哪：把一个"删除失败"变成"悄悄销毁"是最糟的结果。

## 提示词是怎么拼的

面板「这次实际发出去的提示词」里能看到全文，它不是隐藏行为。结构是：

1. **身份约束** —— 以参考照片为唯一依据，五官、脸型、发型发色、肤色、身材比例、服装
   鞋子都不许改，不许美化、换风格、改年龄。
2. **画面类型** —— 角色转身参考图：同一人物、同一站姿、同样的光照，全身入画。
3. **角度清单** —— 按顺序点名每个角度（`front view`、`left side view`、`back view`、
   `low angle view … looking up`、`high angle view … looking down`）。用英文是因为
   模型就是这样被标注的；中文只在界面里出现。
4. **背景 + 你的补充要求 + 画风后缀**。

负向词里除了常规的畸形手、水印，设定图模式还会额外压制"画成好几个不同的人"和
"同一个姿势镜像复制"——这是多视图提示词最常见的两种失败。

## 已知局限

- **仰视角度不够准**。实测五视图里"俯视 45°"是准的（能看到头顶和肩线），但"仰视 45°"
  经常画成接近平视。提示词里已经明确写了动的是机位、人物站姿和视线不变，模型仍然倾向
  把"从下往上看"理解成抬下巴。要多试几张，或改用单视图模式单独抽这一个角度。
- 设定图里每行最多 3 个：画布宽度上限 2048 px，单行 5 个的话每个人物只剩 410 px，
  所以超过 3 个角度会自动折成两行（单格 512–660 px）。
- 提示词里点名了"恰好 N 个角度"，模型偶尔仍会多画或少画一格。要多试，或改用
  「每角度一张」——那种模式下每个角度是独立一次生成，不可能串格。

## 排错

- **面板顶上出现红字**：那就是原因，按它写的改。最常见的两类是 ComfyUI 没开，和没有
  Qwen-Image 2.1 系列模型。
- **出图很慢**：设置页能看到显存。显存不足时 ComfyUI 会把模型分块搬进内存，速度会掉
  几倍。关掉占显存的程序，或者把设置里的「出图尺寸」降到 1.0 MP。
- **人物不像**：换一张更清晰的正面全身照；在「补充要求」里把不变的特征写清楚
  （发型、痣、眼镜、服装）；三视图用「一张设定图」而不是「每角度一张」。
- **设定图里人物数量不对**：`count` 设成 1，尺寸别低于 1 MP；提示词里已经在点名
  "exactly N views"，如果还错就改成「每角度一张」。

## 代码结构

```
lib/
  index.js        宿主半入口：装配 API、注册 agent 工具、挂 web 路由
  api.js          唯一实现：状态、角色、照片、出图、文件操作、回收站
  angles.js       纯函数：角度定义、角度展开、提示词编译（无 I/O，可单测）
  comfy/client.js ComfyUI HTTP 客户端（/prompt /history /view /upload/image /queue）
  comfy/graph.js  程序化构图：Qwen-Image 2.1 + 参考图 + 图校验
  comfy/preferred.js 模型偏好、采样预设、显存评估
  paths.js        资源路径的唯一来源（store 与 trash 都要用，独立成模块避免循环依赖）
  store.js        角色库：索引 JSON + 图片文件，写入串行化
  trash.js        回收站：照片的移动、恢复、清空（只搬字节，索引交给 store 回调）
  runs.js         可轮询、可取消、重启后仍可见的任务注册表
  tools.js        agent 工具（全部转调 api.js）
  client.js       界面半：侧边栏面板、灯箱预览、设置页、回收站
```

`verify-geometry.mjs` 值得单独说一句：面板要实时显示输出尺寸，所以几何算法存在两份——
`lib/angles.js` 是真正出图用的那份，`lib/client.js` 里那份负责画预览。多一次来回请求才能
算出来的话控件会卡，所以复制是有理由的；但**预览只要有一点不准，就变成了一个两分钟之后
才被拆穿的谎**。这个测试就是钉住这两份不许分叉。
